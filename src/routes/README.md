# The app, and the chain behind it

What is written by hand, what is generated, who generates it, and who reads it.
Nothing in `src/lib/generated/` is edited: those files are output, git-ignored,
and rebuilt by `npm run build:css`.

The rule the chain follows: **the compiled CSS is the source of truth for what
classes exist.** Not the SCSS sources — class names are interpolated there
(`_mixins.scss` writes `.#{$prefix}-#{$color}`), so `.btn-primary` exists in no
source file. Anything that needs to know what the kit ships reads `kit.css`.

The theme is the other way round, and deliberately (ADR 0010): the generator's
schema is hand-written TypeScript, because one control writes several variables
and no stylesheet can say that. The two are held together by a check rather
than by generation — see below.

## The chain

```
src/scss/components/*.scss ─┐
src/scss/_defaults.scss     ├─ scripts/build-css.mjs (sass)
src/scss/reset.scss ────────┘        │
                                     ▼
                            static/kit.css        static/reset.css
                                     │
                                     ▼
                       scripts/gen-classes.mjs
                       (× the AXES / FLAGS / PARTS blocks
                          in src/lib/components/*.svelte)
                                     │
                                     ▼
                       src/lib/generated/classes.ts
                                     │
           ┌─────────────────────────┴───────────────┐
           ▼                                         ▼
  src/routes/components/doc.ts              src/lib/index.ts
  (+ the hand-written prose in
   src/routes/components/docs/*.svelte)


static/themes/*.css ────── scripts/build-themes.mjs ──▶ pass / fail
   (19 files, the source)    (parse, re-serialise, compare byte for byte)

src/lib/theme/presets.ts holds NAMES and URLS, not values: the form loads a
theme by fetching the file, so what it reads is what you download.
```

## The five checks

All run in `npm run build:css`, and each exists because the halves it
compares are written by different hands.

- **`gen-classes.mjs` fails** when `kit.css` ships a `.prefix-*` class that no
  component classifies as an axis value, a flag or a part. That class is
  either a variant nobody exposed or a part nobody renders, and both need a
  human. It also warns about a class no documentation page claims.

- **`check-theme-vars.mjs` fails** when a control writes a variable
  `_defaults.scss` does not declare, or when a variable declared under a
  section's prefixes is reachable from no control and named in no `internal`
  list. Both directions, because a variable nobody can set is as much a bug
  as a control nobody reads.

- **`build-themes.mjs` fails** when a shipped theme does not survive being
  read back and regenerated byte for byte. That is what the sentinels are
  for: a flat file of numbers cannot say "push" on its own.

- **`check-defaults.mjs` fails** when the form's neutral and
  `_defaults.scss` disagree on a literal. A theme file carries only what
  DIFFERS from the neutral, so when the form believes X and the stylesheet
  draws Y, a theme that wants X writes nothing and renders as Y. That is how
  `daisy-retro` asked for 0.25rem selectors and shipped with 0.5rem ones — in
  a repo where the three checks above were green. Fourteen disagreements the
  day it was written.

- **`check-scope.mjs` fails** when a variable is declared in the wrong scope,
  in any of three ways: a resolution frozen on `:root`, an input whose
  inheritance is blocked on `:where(*)`, or a variable that is both and
  therefore cannot be declared correctly anywhere. See ADR 0012 — this one
  had bitten four times before it existed.

The last two are the ones to understand if you only read one thing here: a
variable can be **declared, reachable, round-tripping and still wrong**, and
wrong in a way that shows up only in a scope. They are the checks for that.

## The routes

| route | what it is |
| --- | --- |
| `/` | the theme generator: the form, the live preview, the file to copy |
| `/description` | the control → variable table — the documentation of the theme format |
| `/components/<id>` | one component: what it is, its classes, its props, its examples |

The app itself is painted by one shipped theme, and the DRAFT is scoped to the
preview — so a contrast you push far enough to make the form unusable only
makes the preview unusable. That scoping is the whole reason ADR 0012 exists:
it does not work unless every variable is declared in the right place.

## Hand-written, and why

- `src/lib/components/*.svelte` — the wrappers. Each carries an
  `AXES` / `FLAGS` / `PARTS` block declaring what its classes ARE.
- `src/routes/components/docs/*.svelte` — the prose and the examples. WHICH
  classes exist is not written here; `namespaces` is, because nothing else can
  know that `.title` belongs to `text`.
- `src/lib/theme/sections/*.ts` — the generator's controls, their help text,
  and the arithmetic that turns an answer into variables.
- `src/lib/theme/presets.ts` — the nineteen themes' names and URLs. The
  values are in `static/themes/*.css`, which is the source.
